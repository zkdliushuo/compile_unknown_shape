\section{System Design of \mysys}
\label{sec:design}

\input{figures/sys-design/mysys-workflow}

We propose \mysys, a highly accurate constant propagation framework that infers constant parameter values of kernels from DL frameworks.
The workflow of \mysys is shown as \autoref{fig:overall_workflow}.
\mysys takes the DL model's specific constant information as input.
It first generates the calling context for each operator invocation (\S\ref{sec:design:context_construction}).
Next, \mysys identifies all the early-exit paths (\S\ref{sec:design:early-return}) and performs context-sensitive inter-procedural constant propagation along normal paths (\S\ref{sec:design:propagation}).
At the end of the analysis, the derived constant schedule parameters of the kernel function are used to perform kernel specialization, generating specialized kernel binaries or eliminating redundant kernel instantiations (\S\ref{sec:design:specialization}).

\subsection{Definitions}\label{sec:design:definitions}

To formally describe the analysis of \mysys, we first define the abstract domains and notations used in our framework, as summarized in \autoref{fig:abstract-domain}.

\textit{Memory Model and Variables.}
We distinguish between SSA values and memory locations:
\begin{itemize}
    \item \kw{Top-level variables} ($v \in \mathcal{V}$) correspond to virtual registers in the LLVM IR.
    \item \kw{Base objects} ($b \in \mathcal{B}$) represent the abstract base addresses of memory blocks created at allocation sites (e.g., \texttt{alloca} instructions, global variables, or heap allocations).
    \item \kw{Memory locations} ($o \in \mathcal{O}$) represent specific fields within allocated objects. A location is defined as a pair $\langle b, \delta \rangle$, where $\delta \in \mathbb{Z}$ denotes a concrete byte offset relative to the base address $b$.
\end{itemize}

\textit{Abstract Values and Lattice.}
The analysis tracks the state of variables using \kw{Specialized Values} ($sv \in \mathcal{SV}$). The domain $\mathcal{SV}$ forms a lattice comprising the following elements:
\begin{itemize}
    \item \kw{Top ($\top$) and Bottom ($\bot$):} $\top$ represents an \textit{undefined} or \textit{uninitialized} state, while $\bot$ represents a generic \textit{variable} state where the value cannot be statically determined.
    \item \kw{Concrete Constants ($c$):} These represent precise, known values. This category includes integers ($\in \mathbb{Z}$), floating-point numbers ($\in \mathbb{R}$), and \kw{Function Objects} ($f \in \mathcal{F}$), which represent references to functions targeted by direct or indirect calls.
    \item \kw{Abstract Pointers ($p$):} Defined structurally as $\langle b, \hat{\delta} \rangle$. A pointer $p$ represents an address computed by adding an \kw{Abstract Offset} $\hat{\delta}$ to a base object $b$. Here, $\hat{\delta} \in \mathbb{Z} \cup \{\bot\}$ allows the analysis to track precise offsets when possible, or degrade to $\bot$ if the offset is variable (e.g., a runtime index).
\end{itemize}

\textit{Context and State.}
The program state and inter-procedural context are captured by the following mappings:
\begin{itemize}
    \item The \kw{Environment} $\mathbb{E}: \mathcal{V} \mapsto \mathcal{SV}$ maps top-level virtual registers to their abstract values.
    \item The \kw{Store} $\mathbb{S}: \mathcal{O} \mapsto \mathcal{SV}$ maps memory locations to the values stored therein. By mapping from pairs of $\langle b, \delta \rangle$, the store naturally supports field-sensitive tracking of structure fields and array elements.
    \item The \kw{Calling Context}~$\mathbb{C} := (\mathbb{E}, \mathbb{S})$ encapsulates the analysis state (environment and store) at the entry basic block of the current function. This context is determined by the caller and propagates constraints across function boundaries during inter-procedural analysis.
\end{itemize}

\subsection{Calling Context Generation for C++}\label{sec:design:context_construction}

\autoref{fig:context_workflow} illustrates the overall workflow of context generation in \mysys{}.
The design bridges the gap between the high-level Graph IR and the low-level C++ execution state through two phases:
(1) \textbf{Extraction} (\ding{172}--\ding{174}), which parses the IR node to generate structured metadata; and
(2) \textbf{Construction} (\ding{175}--\ding{178}), which applies semantic rules to this metadata to reconstruct the C++ memory state.

\subsubsection{Extract Context Metadata from Graph IR}\label{sec:design:extract}

\mysys{} integrates context generation directly into the graph compilation phase.
To explain how \mysys{} bridges the semantic gap between High-Level IR and Low-Level C++, we consider a concrete example using the \texttt{flash\_attention} operator.
The C++ implementation of this operator is defined with a specific function signature, which determines the data types and order of arguments expected at the binary level. A simplified signature is shown below:

\begin{center}
\texttt{flash\_attention(Tensor query, ..., SymInt[]? seq\_lengths=None, int num\_heads=1)}
\end{center}

Here, the signature includes complex types: \texttt{Tensor} represents a multi-dimensional array, \texttt{SymInt[]} denotes an array of symbolic integers (used for dynamic dimensions), and \texttt{?} indicates an \texttt{Optional} type.
Arguments like \texttt{num\_heads} have default values.
Suppose a node in the Graph IR invokes this operator \ding{172}.
During the graph compilation phase, the shape inference pass determines that the \texttt{query} argument has a shape of $[s_1, 40, s_2, 64]$, and the \texttt{seq\_lengths} argument is provided as $[s_3, s_4]$ (where $s_i$ denotes symbolic expressions).

\mysys{} first extracts \ding{173} the \textit{context metadata} \ding{174} by aligning the IR node's arguments with the formal parameters of the C++ signature.
This alignment ensures two things: (1) explicit arguments from the IR are captured with their inferred shapes and values; and (2) implicit arguments (like \texttt{num\_heads}) are filled using the default values from the signature.

The context metadata $\Phi$ is a sequence $[\mathcal{M}_0, \mathcal{M}_1, \dots, \mathcal{M}_n]$, where each $\mathcal{M}_i$ is a tagged union capturing the type and value information.
To support the nested structures seen in the example (e.g., Optional, Array), we parameterize container types with an element type $\tau$:
\begin{equation}
  \mathcal{M} ::= \textsc{Scalar}(c) \mid \textsc{String}(s) \mid \textsc{Tensor}(\vec{d}) \mid \textsc{Array}\langle\tau\rangle(\vec{e}) \mid \textsc{Optional}\langle\tau\rangle(v)
\end{equation}
Here, $c$ is a scalar value, $s$ is a string, $\vec{d}$ is the tensor dimension list, $\vec{e}$ is a sequence of elements, and $v$ is an optional value.
This intermediate representation $\Phi$ captures the complete runtime state required for context reconstruction, independent of the complexities of FFI glue code.
For the above example of the \texttt{flash\_attention} operator, \mysys{} extracts these metadata: \texttt{query} maps to $\textsc{Tensor}([s_1, 40, s_2, 64])$, \texttt{seq\_lengths} maps to $\textsc{Optional}\langle\textsc{Array}\langle\textsc{Scalar}\rangle\rangle([s_3, s_4])$, \texttt{num\_heads} maps to $\textsc{Scalar}(1)$, retrieved from the default value.
Hence the context metadata $\Phi_{\texttt{flash\_attention}} = [\textsc{Tensor}([s_1, 40, s_2, 64]), \dots, \textsc{Optional}\langle\textsc{Array}\langle\textsc{Scalar}\rangle\rangle([s_3, s_4]), \textsc{Scalar}(1)]$.

\subsubsection{Update Call Context of C++ Entry Function using Context Metadata}\label{sec:design:update}

The goal of the second phase is to synthesize the initial C++ calling context \ding{178}, denoted as $\mathbb{C}_{init} = (\mathbb{E}, \mathbb{S})$.
The Environment $\mathbb{E}$ maps function arguments to their specialized values, while the Store $\mathbb{S}$ stores the data in memory.
Starting with an empty context $\mathbb{C}_{0}$ \ding{176}, \mysys{} iterates through the context metadata $\Phi$, sequentially updating \ding{175} the abstract state:
\begin{equation}
\mathbb{C}_{init} = \mathcal{R}_{\mathcal{M}_n} \circ \dots \circ \mathcal{R}_{\mathcal{M}_1} \circ \mathcal{R}_{\mathcal{M}_0} (\mathbb{C}_0)
\end{equation}
For each metadata item $\mathcal{M}_i$, we apply a semantic modeling rule $\mathcal{R}_{\mathcal{M}_i}$ listed in \autoref{tab:semantic-rules} to transform the high-level metadata into the low-level memory representation by update abstract state $\mathbb{C}_i$.

\subsubsection{Update Rules for Metadata}\label{sec:design:rules}

We define a set of field-sensitive update rules in \autoref{tab:semantic-rules} to handle the mapping from $\mathcal{M}$ to the C++ memory model.
We first define a helper function $\alpha(x)$ to unify concrete and symbolic values:
\begin{equation}
  \alpha(x) =
  \begin{cases}
    x & \text{if } x \text{ is a concrete constant} \\
    \bot & \text{if } x \text{ is a symbolic expression}
  \end{cases}
\end{equation}

\input{tables/semantic-model-rules-for-core-types}

\noindent\textbf{Field-Sensitive Reconstruction.}
The core challenge in this translation is the \textit{deep reconstruction} of composite types.
As shown in \autoref{tab:semantic-rules}, types like \texttt{Tensor} are not single values but structures containing internal pointers (e.g., \texttt{sizes}).
Our rules explicitly allocate memory for these internal fields and link them via internal pointers in $\mathbb{S}$.
For example, when processing the \texttt{query} tensor metadata, \mysys{} first allocates the base object $\ell$ representing the tensor \texttt{query}.
Next, \mysys allocates a logical array $\ell_{sz}$ to store the dimensions $[s_1, 40, s_2, 64]$ and updates the specialized values of the memory location $\langle\ell, \delta_{\text{sizes}}\rangle$ in $\mathbb{S}$ to point to the starting address of array $\langle\ell_{sz}, 0\rangle$.
This ensures that when the downstream analyzer accesses \texttt{query.sizes[1]}, it correctly retrieves the value $40$.

\noindent\textbf{Completeness.}
The rules in \autoref{tab:semantic-rules} cover all five core parameter types (Scalar, String, Tensor, Array, and Optional) used in the PyTorch operator interface.
Recursive rules allow for complex compositions, such as the $\texttt{Optional}\langle\texttt{Array}\rangle$ used in the \texttt{seq\_lengths} example, ensuring the approach is generic across the standard deep learning operator schema.


\subsection{Identify Early Exit Edge}\label{sec:design:early-return}

In production operator libraries, execution status is predominantly managed via compile-time constant integer status codes.
We first define two sets of constants, $\mathcal{S}$ and $\mathcal{E}$, representing success and error states respectively (e.g., $\mathcal{S}=\{0\}$ and $\mathcal{E}=\{-1\}$ for CANN operator libraries).
The identification of early-exit edges relies on analyzing the \textit{conditional return-value flow} within functions containing shape checkers.

            \State $\texttt{MarkEarlyExitEdge}(B_{src} \rightarrow B_{dst})$
            \State $E_{exit} \gets E_{exit} \cup \{B_{src} \rightarrow B_{dst}\}$
          \EndIf
        \EndFor

\subsubsection{Conditional Return-Value Flow Graph Construction}

Our method constructs a \textit{Conditional Return-Value Flow Graph} (CRVFG) to precisely capture the relationship between shape checker conditions and early-exit paths.
The CRVFG is built \textit{on-demand} and \textit{intra-procedurally}, with two key characteristics that ensure efficiency:

\begin{enumerate}
    \item \textbf{On-Demand Construction:} We construct the value flow graph only for functions that explicitly contain shape checkers, rather than for all functions in the program. This selective construction avoids the overhead of analyzing functions irrelevant to shape checking.
    
    \item \textbf{Return-Value Focus:} We exclusively track the value flow of return values. In SSA-form IR, return values of functions containing shape checkers are typically top-level variables (indicating whether shape checks succeeded), rarely involving implicit value flows through memory objects. Consequently, the resulting value flow graph is remarkably small and efficient to analyze.
\end{enumerate}

\autoref{fig:conditional-value-flow} illustrates the CRVFG for the \texttt{set\_t} function.
The graph captures the conditional predicate $\varphi_1 = (\%1 = \text{true})$, where $\%1 = \texttt{icmp ne \%0, 0}$, that guards the error return path.
This establishes the data-flow relationship between the shape check condition and the error return value $\%0$ (the return value of \texttt{check}).

\subsubsection{Error Status Determination via Constant Comparison}

A key advantage of our approach is that determining whether a return value indicates an error state under a given condition requires only simple constant comparison, without invoking an SMT solver.
Since shape checker conditions in operator libraries typically involve equality or inequality comparisons against predefined status code constants, we formalize the error state determination for a given return value $v$ and its governing condition $\varphi$ as follows:

$$
    \text{isError}(v, \varphi) = 
    \begin{cases}
        \text{true} & \text{if } \varphi \Rightarrow (v \notin \mathcal{S}) \lor \varphi \Rightarrow (v \in \mathcal{E}) \\
        \text{false} & \text{if } \varphi \Rightarrow (v \in \mathcal{S}) \\
        \text{unknown} & \text{otherwise}
    \end{cases}
$$

In practice, conditional guards for shape checkers often test for inequality against success codes (e.g., $v \neq 0$). Thus, proving that $v \notin \mathcal{S}$ is strictly sufficient to identify an error path. This determination reduces to straightforward set membership tests against $\mathcal{S}$ and $\mathcal{E}$, bypassing complex constraint solving.

\subsubsection{Early-Exit Edge Identification Algorithm}

Based on the CRVFG and the error status determination, we propose an early-exit edge identification algorithm to locate all control-flow edges that lead to early exits. The algorithm takes a function $F$ containing shape checkers, along with the predefined success and error status code sets $\mathcal{S}$ and $\mathcal{E}$. The process begins by obtaining the return instruction and its specific return value $v_{ret}$ via $\texttt{GetReturnInst}(F)$ and $\texttt{GetReturnValue}(inst)$. We then construct the Conditional Return-Value Flow Graph by calling $\texttt{BuildCRVFG}(F, v_{ret})$, which traces the value definitions backwards to yield a set of conditional value-flow edges. For each edge, we extract the associated condition predicate $\varphi$ ($\texttt{GetCondition}(edge)$) and the value $v$ flowing along it ($\texttt{GetValue}(edge)$). Applying the $\texttt{isError}(v, \varphi)$ logic, we evaluate whether this data flow represents an error return path. If confirmed, we trace back to the source basic block $B_{src}$ ($\texttt{GetSourceBlock}(edge)$) and locate the precise conditional branch instruction matching $\varphi$ ($\texttt{FindBranchWithCondition}(B_{src}, \varphi)$). Finally, we determine the branch's successor block $B_{dst}$ taken when $\varphi$ evaluates to true ($\texttt{GetSuccessor}(br, \varphi)$) and formally mark the control-flow transition from $B_{src}$ to $B_{dst}$ as an early-exit edge ($\texttt{MarkEarlyExitEdge}(B_{src} \rightarrow B_{dst})$).

For the \texttt{set\_t} function shown in \autoref{fig:set_t_cfg}, the CRVFG in \autoref{fig:conditional-value-flow} reveals that when condition $\varphi_1 = (\%1 = \text{true})$ holds, the return value $\%0 \in \mathcal{E}$ (error set). Therefore, the edge from BB0 to BB1 (the error path where $\%1$ is true) is marked as an early-exit edge. This edge corresponds to the branch where the condition $\texttt{icmp ne \%0, 0}$ evaluates to true, indicating that the shape check failed.


\subsection{Inter-Procedural Information Propagation for Host-Side Programs}\label{sec:design:propagation}

Our primary objective is to optimize the performance of device kernel functions and eliminate those kernels not called at runtime.
To this end, \mysys employs a unified inter-procedural analysis framework integrating pointer analysis, function object propagation, and scalar constant propagation for the host-side programs.
\mysys propagates precise semantic information up to the kernel launch sites.
Operating on the CFG, the analysis maintains a symbolic environment $\mathbb{E}$ and a flow-sensitive memory store $\mathbb{S}$.
We detail the handling of key program constructs below.

\textit{Pointer Arithmetic and Alias Analysis}
We represent a pointer value as a pair $\langle \mathcal{B}, \delta \rangle$. 
For pointer arithmetic (e.g., \texttt{getelementptr}), we update the offset $\delta$ while preserving the base set $\mathcal{B}$.
To balance precision and overhead, we bound $|\mathcal{B}| \le 5$, demoting the base to \texttt{Unknown} if this limit is exceeded.
Function pointers are similarly propagated to support indirect calls.
To refine alias analysis when bases are unknown, we leverage LLVM's Type-Based Alias Analysis (TBAA) metadata to restrict the scope of potential memory conflicts to type-compatible objects.

\textit{Memory Operations}
The memory store $\mathbb{S}$ is updated and accessed by three primary instructions.
Allocation instructions introduce new abstract locations into $\mathbb{S}$, managed with context-sensitive modeling.
Store instructions update the flow-sensitive store $\mathbb{S}$ local to the current basic block: writing to a pointer with a deterministic base performs a \kw{strong update} (replacement), whereas writing to an unknown base or offset triggers a \kw{weak update} (conservative invalidation/merge).
Load instructions simply retrieve the current specialization value from $\mathbb{S}$ corresponding to the accessed address.

\textit{Context-Sensitive Function Calls}
We employ a context-sensitive approach akin to abstract interpretation.
Each call site generates a specialized calling context based on the actual arguments and the current store $\mathbb{S}$.
The algorithm recursively analyzes the callee, using memoization to cache results for identical contexts.
Recursion is handled by tracking the call stack and returning $\bot$ upon detecting cycles, ensuring termination.

\textit{Control Flow Processing}
We adopt a hybrid strategy for loops, prioritizing a \kw{Per-Iteration Analysis} that simulates execution iteration by iteration.
If loop conditions become non-constant, the analysis falls back to a \kw{Maximal Fixed-Point (MFP)} iteration.
Within these modes, conditional branches determine edge liveness: if a condition evaluates to a constant, the non-taken edge is marked \texttt{Inactive}; otherwise, both branches are marked \texttt{Active}.
This liveness information is critical for pruning unreachable paths during propagation.

\textit{Context Merging and Early-Exit Integration}
At control flow convergence points, we merge the incoming stores $\mathbb{S}$ from all \texttt{Active} predecessors and merge incoming specialization values for \texttt{PHI} instructions.
The merging applies standard lattice operations.
Crucially, this step integrates with the optimization described in \cref{sec:design:early-return}.
Any predecessor edge marked as an \texttt{early-exit} path, or determined to be unreachable by the branch analysis, is treated as \texttt{Inactive}.
Consequently, the memory states and values from these inactive blocks are excluded entirely from the merge operation.
This prevents the pollution of the analysis state by imprecise or error-handling logic, significantly improving the precision of the propagated information at join points.

\subsection{Kernel Specialization and Library Pruning} \label{sec:design:specialization}

Based on the context derived from the inter-procedural analysis, \mysys performs two key optimizations: generic kernel specialization and pruning redundant template instantiations for manually specialized libraries.

For generic kernels, \mysys substitutes the variable inside the kernel with the concrete schedule parameters identified from the analysis on the host-side program.
Then \mysys employs a sequence of optimization passes, specifically \texttt{IPSCCP}, \texttt{Loop Unrolling}, and \texttt{CFG Simplification}. 
These passes exploit the newly introduced constants to fold computations and simplify control structures, generating a highly optimized kernel binary.

For manually specialized libraries, \mysys reduces code size by leveraging path liveness information from the host analysis.
During constant propagation, we identify \texttt{Dead Paths}, i.e., execution branches where guard conditions are evaluated to be false based on deterministic constants.
If a specific template function instance is invoked only on these dead paths, \mysys determines it is unreachable at runtime and removes the instance entirely.
This selective pruning ensures that only potentially active operator instances are retained in the final binary.
