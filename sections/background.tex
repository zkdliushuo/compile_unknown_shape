\label{sec:motivation}

Next, we analyze the challenges and present our design insights (\S\ref{sec:motivation:challenges}).

\subsection{Motivation of Automatic Kernel Specialization}
\label{sec:motivation:auto-spec}

This section elucidates the opportunity for kernel specialization by tracing the flow of constant values across the software stack and demonstrates the necessity of this approach by analyzing the bottlenecks inherent in generic kernels on a specific hardware platform, the Ascend~\cite{liao2019davinci}, a kind of widely employed AI accelerators.

\subsubsection{Cross-Layer Constant Value Flow}
\label{sec:motivation:flow}

The \textbf{\textit{partial dynamics}} characteristic of DL models implies that while input tensors vary, there are many \initialconsts.
\autoref{fig:motivating-example} illustrates how these constants propagate through the software stack.
When a Python-level operator (e.g., \texttt{torch.fa}) is invoked, arguments flow through the FFI layer to the Host C++ library.
While some parameters are runtime-dependent (e.g., batch size), others are derived from the fixed model configuration (e.g., number of attention heads $h=40$).
Subsequently, within the Host C++ runtime, the software pipeline depth (i.e., \texttt{stages}) are computed based on $h$ to configure the memory access latency hiding inside the kernel \texttt{kernel\_fa}.

This observation suggests an opportunity: by statically tracking \initialconsts from the Python front-end down to the kernel launch, we can identify runtime invariants that are currently treated as variables.
For generic kernels, this enables aggressive specialization of the device code.
Furthermore, for manually specialized libraries, this allows to identify the specific kernel instantiations not matching the derived compile-time constants.
This facilitates the pruning of unreachable code paths for a specific model, mitigating binary bloat.

\subsubsection{Disadvantages of Generic Kernels and Manually Specialized Libraries}
\label{sec:motivation:disadvantages}

\textit{Bottleneck Analysis for Generic Kernels.}
Operator libraries for Ascend still have to adopt generic kernels, mainly due to their complex schedule strategies and the great number of schedule parameters.
In this design, almost all schedule parameters are passed as runtime arguments from the Host.
Since the compiler treats these parameters as variables, it cannot perform aggressive optimizations like constant folding.
To understand the impact of this design, we examine the execution flow on Ascend, a DL accelerator based on SIMD execution model, as shown in \autoref{fig:fa_on_ascend}.

On Ascend, the Cube and Vector units execute the primary tensor operations (e.g., MatMul on Cube and Softmax on Vector), while the architecture provides sophisticated programmable memory hierarchies.
The kernel must explicitly manage the chunk size and data layout at every level, as well as the data movement and layout transformations between these levels.
Besides, the Scalar unit acts as the central control unit, responsible for scalar data process, instructions dispatch, and handling control flows (such data paths are indicated by red dashed lines, for simplicity we only display some of them).
For example, the kernel moves a tile of the tensor $Q_{GM}$ from the global memory (GM) to the L1 memory unit per time, denoted as $Q_{L1}$.
The Scalar unit is responsible to calculate the starting address of the data movement based on the input shapes, layout strides, tile factors on all dimensions, pipeline depths.

In generic kernels, the Scalar unit may be over-occupied.
Since the Scalar unit typically possesses much lower computing power than a general-purpose host CPU, excessive scalar calculations related to schedule parameters can overload the unit.
Worst, too many scalar intermediates may causes registers spill since there are only 32 general-purpose registers. 
As a result, the powerful Cube and Vector units will stall to await instruction dispatch or scalar operands.
Furthermore, generic kernels often involve complex control flows (e.g., branching to handle different operator variants), which exerts heavy pressure on the instruction cache (I-Cache).
Frequent instruction jumps in such complex logic inevitably lead to I-Cache misses and pipeline flushes.
Finally, when loop bounds remain unknown at compile time, the compiler struggles to perform loop unrolling. 
Consequently, instruction scheduling is confined to the scope of a single iteration, preventing the effective overlapping of memory access and computation.

We further study this impact by profiling key operators from the \textbf{Qwen2-1.5B} model on the Ascend NPU.
\autoref{fig:perf_stats} presents the ratio of scalar instructions and I-Cache miss rates.
The data reveals that LLMs' operators exhibit high proportion of scalar instructions and suffer from considerably high I-Cache miss rate.

\textit{Code Bloat in Manually Specialized Libraries.}
High-performance GPU libraries like FlashInfer~\cite{ye2025flashinfer} rely on C++ template metaprogramming to enable aggressive compiler optimizations. 
To avoid runtime JIT overhead in serving scenarios, these libraries must pre-instantiate kernels for the Cartesian product of all template parameters.
Taking FlashInfer as an example, where template parameters are denoted as $\mathcal{T} = \langle D, M, G, P, T_{tile} \rangle$, covering standard head dimensions ($D \in \{64, 128, 256\}$), mask modes ($M \in \{None, Causal\}$), diverse GQA sizes ($G \in \{1, 2, 4, 5, 6, 7, 8\}$), Position Embedding ($P \in \{None, RoPE, ALiBa\}$) and $\sim 10$ different tile size configurations $T_{tile}$ results in over 1000 binary instantiations.

This design causes significant binary bloat.
For a specific deployment like \textbf{Qwen2-1.5B} ($D=128, G=6, M=Causal, P=RoPE$), the runtime utilizes only about 10 kernel instantiations.
Consequently, relative to the $\sim 1000$ available kernels, most kernels are dead for a given model.
Crucially, while this pre-instantiation strategy is manageable on GPUs due to relatively simple schedule, it is ill-suited for Ascend.
As discussed in \S\ref{sec:motivation:disadvantages}, achieving peak performance on Ascend requires a massive set of fine-grained schedule parameters.
The resulting combinatorial explosion makes static specialization infeasible, forcing Ascend libraries to rely on suboptimal generic kernels.

\subsubsection{Why Automatic Kernel Specialization is Beneficial?}

Our analysis of kernel parameters in \autoref{fig:param_stats}, which breaks down the schedule parameters of representative kernels into variable and invariable categories, reveals a critical insight: the overwhelming majority of kernel parameters are runtime invariants.
By globally propagating \initialconsts to resolve most schedule parameters at compile time, there are twofold benefits.
First, for operator libraries adopting generic kernels, this enables the generation of model-specific specialized kernels. 
The compiler can perform aggressive constant folding on these parameters, drastically reducing scalar instruction overhead and simplifying control flow to minimize I-Cache misses.
Second, this approach effectively addresses code bloat in manually specialized libraries.
In such libraries, the host runtime calculates schedule parameters to dispatch specific pre-compiled kernel instantiations.
Once these parameters are statically derived via constant propagation, the unreachable kernel dispatch path becomes deterministic.
This allows us to identify kernel instantiations called at the unreachable paths, enabling the precise pruning of unused binaries to retain only the minimal code set required for the specific model deployment.

\subsection{Challenges and Design Insights}
\label{sec:motivation:challenges}

To achieve automatic kernel specialization, it requires analyzing the value flow from Python down to C++, which presents two major challenges that cannot be properly addressed by the existing static analysis.

\subsubsection{Challenge 1: The cross-language semantic gap.}

Achieving high-precision, context-sensitive cross-language analysis fundamentally relies on the accurate reconstruction of the calling context for C++ operators. 
Modern DL systems extensively leverage FFI mechanisms (e.g., Pybind11~\cite{pybind11}, CPython C API~\cite{pythoncapi}) to invoke underlying C++ operators, whose input parameters (e.g., Tensors) are typically instantiated and initialized on the Python side. 
However, the FFI layer is replete with complex \textit{glue code}, involving implicit type conversions, dynamic dispatch mechanisms, and reference counting, which creates a significant semantic gap between Python and C++. 
This poses a severe challenge for traditional source-based cross-language analysis methods.

Existing cross-language analysis works~\cite{kan2024taint4javac,Monat2021PythonC} primarily rely on abstract interpretation techniques to address general multi-language interoperability issues (e.g., Python-C, Java-C). 
Nevertheless, these methods face significant challenges when applied to DL systems due to two main limitations:
\begin{enumerate}
    \item \textbf{Lack of Domain Awareness:} 
    Existing tools typically model generic FFI APIs (such as JNI~\cite{jni} or the Python C API~\cite{pythoncapi}) as black boxes or simple data conduits. 
    They fail to comprehend the complex \textit{domain-specific objects} within DL systems, particularly the deep heap memory layouts and internal indirect reference relationships. 
    For instance, consider a Tensor \texttt{q} constructed on the Python side with a shape of \texttt{(\%B, 40, \%S, 64)} as shown in \autoref{fig:motivating-example}. Generic analyzers struggle to trace the heap memory state associated with the C++ \texttt{sizes} pointer (i.e., establishing the structural constraints between the Python shape attribute and the underlying C++ array).
    \item \textbf{Efficiency and Precision Bottlenecks:} 
    When dealing with massive DL libraries, performing full interpretation of dynamic language source code is inefficient. Furthermore, it struggles to accurately deduce the side effects of complex C++ internal heap allocations from the Python side, leading to over-approximated analysis results.
\end{enumerate}

\textit{Insight: semantic modeling core data types in DL systems.}
Instead of the traditional paradigm of analyzing FFI control flows, we propose a cross-language semantic modeling approach. 
Our methodology is grounded in two key observations:
\begin{enumerate}
    \item \textbf{Finite and Stable Core Types:} Data types used for cross-language interaction in DL systems are highly convergent and stable (\texttt{Tensor}, \texttt{Array}, etc.). 
    This stability enables us to perform comprehensive and precise semantic modeling of these core types.
    \item \textbf{Extract Constant Information from Graph IR:} The DL system compiles DL models and represents models using Graph IR (e.g. ATen IR).
    The instructions in the Graph IR contain precise information regarding operator input parameters. 
    By leveraging this information, we can directly extract the semantic values of parameters, bypassing the need for expensive or imprecise analysis of Python source code.
\end{enumerate}

Building on these insights, we directly map computation graph node information to the abstract states of C++ entry functions. 
By bridging the language boundary through type system modeling, we achieve high-precision reconstruction of C++ contexts while avoiding the overhead of analyzing complex FFI glue code.
\subsubsection{Challenge 2: Shape Checkers Leading to Early-Exit Paths}

Operator libraries enforce hardware and semantic constraints (e.g., memory alignment, dimension equality) through runtime shape checkers. These checks depend on dynamic dimensions; violating them triggers an early exit with an error status code.

Consider Flash Attention as an example. Its computation is defined as:
\begin{equation*}
    \text{Attention}(Q, K, V, M) = \text{softmax}\left(\frac{QK^\top}{\sqrt{d_k}} + M\right) V
\end{equation*}
This operator imposes strict constraints on dynamic dimensions, such as matching batch sizes ($B_q = B_k = B_v$) and sequence lengths ($S_k = S_v$).

\autoref{lst:early_return_code} demonstrates how these shape checkers impede optimization. The function \texttt{set\_t} verifies if sequence lengths \texttt{sq} and \texttt{sk} match. Since these dimensions are dynamic, the compiler cannot statically guarantee the check passes. Consequently, standard path-insensitive analysis conservatively merges data flows from both the success path (where \texttt{t=32}) and the early-exit path (where \texttt{t} remains uninitialized/unknown).
As shown in \autoref{fig:dynamic_shape_check_demo}, this merging "pollutes" the value of \texttt{t} at the exit block (BB3), causing the compiler to treat the constant 32 as a variable. This prevents constant propagation. While symbolic execution~\cite{Cadar2008KLEEUnassistedAutomatic,Yao2024FalconFusedApproach} can distinguish these paths, it is often prohibitively expensive due to path explosion.

\textit{Insight: Conditional Return-Value Flow for Early-Exit Edge Identification.}
Our approach is grounded in the invariant that kernels are only launched for valid inputs. We observe that functions containing shape checkers exhibit a distinctive structural property: their return values are determined by conditional expressions that distinguish between success and error status codes.

Unlike pattern-based matching approaches, we propose a \textit{conditional return-value flow} analysis to precisely identify early-exit edges. The key insight is that for functions containing shape checkers, the return value's data flow, combined with its governing conditional expressions, directly reveals which control-flow edges lead to error returns. Specifically, we construct a lightweight value flow graph for the return value within each function, tracking how the return value depends on conditionally guarded expressions. By determining whether the return value belongs to a predefined error status code set under specific path conditions, we can identify the conditional branch that guards the early-exit path. The edge corresponding to this condition is then marked as an early-exit edge.

This approach offers significant advantages over general-purpose value flow analysis: (1) the value flow graph is constructed \textit{on-demand} only for functions explicitly containing shape checkers, avoiding unnecessary overhead; (2) the analysis focuses exclusively on return values, which in SSA-form IR are typically top-level variables that rarely involve complex memory object flows, resulting in very small graphs; and (3) determining whether a return value indicates error under a given condition requires only simple constant comparison against predefined status code sets, eliminating the need for expensive SMT solving. By marking these early-exit edges, we shield the forward data-flow analysis from values on error paths, achieving path-sensitive precision without the computational overhead of symbolic execution.
