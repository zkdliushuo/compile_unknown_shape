\section{Background and Motivation}
\label{sec:motivation}

In this section, we use the Flash Attention (FA) operator from PyTorch's operator library as a running example to illustrate our motivation and the challenges of constant specialization.
We first introduce the FA operator definition.
Given query, key, and value tensors $Q \in \mathbb{R}^{B_q \times h \times S_q \times d_k}$, $K \in \mathbb{R}^{B_k \times h \times S_k \times d_k}$, $V \in \mathbb{R}^{B_v \times h \times S_v \times d_v}$, and an optional mask $M$, Flash Attention can be denoted simply as:
\begin{equation}
    \text{Attention}(Q, K, V, M) = \text{softmax}\left(\frac{QK^\top}{\sqrt{d_k}} + M\right) V
    \label{eq:flash_attention}
\end{equation}
This operator imposes strict constraints on shape dimensions: batch sizes must match ($B_q = B_k = B_v$), the number of attention heads $h$ must be consistent across $Q$, $K$, and $V$, sequence lengths for $K$ and $V$ must be equal ($S_k = S_v$), and head dimensions must satisfy $d_k = d_v$.
Modern FA implementations support diverse configurations: varying numbers of attention heads ($h \in \{8, 16, 32, 40, \ldots\}$), head dimensions ($d_k \in \{64, 128, 256\}$), mask types (none, causal, sliding window), attention variants (GQA, MLA), and position encodings (RoPE, ALiBi).
These configuration parameters are typically fixed for a given model but vary across different models, making them ideal candidates for compile-time specialization.

In this section, we first illustrate the opportunity for constant propagation across the DL software stack (\S\ref{sec:motivation:auto-spec}).
Next, we analyze the challenges and present our design insights (\S\ref{sec:motivation:challenges}).

\subsection{Motivation of Automatic Kernel Specialization}
\label{sec:motivation:auto-spec}

This section elucidates the opportunity for kernel specialization by tracing the flow of constant values across the software stack. It further demonstrates the necessity of this approach by analyzing the bottlenecks inherent in generic kernels on Ascend~\cite{liao2019davinci}, a widely employed AI accelerator.

\subsubsection{Cross-Layer Constant Value Flow}
\label{sec:motivation:flow}

The \textbf{\textit{partial dynamics}} characteristic of DL models implies that while input tensors vary, there are many \initialconsts.
\autoref{fig:motivating-example} illustrates how these constants propagate through the software stack.
When a Python-level operator (e.g., \texttt{torch.fa}) is invoked, arguments flow through the FFI layer to the host C++ library.
While some parameters are runtime-dependent (e.g., batch size), others are derived from the fixed model configuration (e.g., number of attention heads $h=40$).
Subsequently, within the host C++ runtime, the software pipeline depth (i.e., \texttt{stages}) is computed based on $h$ to configure the memory access latency hiding inside the kernel \texttt{kernel\_fa}.

This observation suggests an opportunity: by statically tracking \initialconsts from the Python front-end down to the kernel launch, we can identify runtime invariants that are currently treated as variables.
For generic kernels, this enables aggressive specialization of the device code.
Furthermore, for manually specialized libraries, this allows us to identify the specific kernel instantiations not matching the derived compile-time constants.
This facilitates the pruning of unreachable code paths for a specific model, mitigating binary bloat.

\subsubsection{Disadvantages of Generic Kernels and Manually Specialized Libraries}
\label{sec:motivation:disadvantages}

\textit{Bottleneck Analysis for Generic Kernels.}
Operator libraries for Ascend still have to adopt generic kernels, mainly due to their complex schedule strategies and the great number of schedule parameters.
In this design, almost all schedule parameters are passed as runtime arguments from the host.
Since the compiler treats these parameters as variables, it cannot perform aggressive optimizations like constant folding.
To understand the impact of this design, we examine the execution flow on Ascend, a DL accelerator based on SIMD execution model, as shown in \autoref{fig:fa_on_ascend}.

On Ascend, the Cube and Vector units execute the primary tensor operations (e.g., MatMul on Cube and Softmax on Vector), while the architecture provides sophisticated programmable memory hierarchies.
The kernel must explicitly manage the chunk size and data layout at every level, as well as the data movement and layout transformations between these levels.
Besides, the Scalar unit acts as the central control unit, responsible for scalar data processing, instruction dispatch, and handling control flows (such data paths are indicated by red dashed lines; for simplicity, only some are shown).
For example, the kernel moves a tile of the tensor $Q_{GM}$ from the global memory (GM) to the L1 memory unit at a time, denoted as $Q_{L1}$.
The Scalar unit is responsible for calculating the starting address of the data movement based on the input shapes, layout strides, tile factors on all dimensions, and pipeline depths.

In generic kernels, the Scalar unit may be over-occupied.
Since the Scalar unit typically possesses much lower computing power than a general-purpose host CPU, excessive scalar calculations related to schedule parameters can overload the unit.
Worse yet, excessive scalar intermediates may cause register spill, as there are only 32 general-purpose registers.
As a result, the powerful Cube and Vector units will stall to await instruction dispatch or scalar operands.
Furthermore, generic kernels often involve complex control flows (e.g., branching to handle different operator variants), which exerts heavy pressure on the instruction cache (I-Cache).
Frequent instruction jumps in such complex logic inevitably lead to I-Cache misses and pipeline flushes.
Finally, when loop bounds remain unknown at compile time, the compiler struggles to perform loop unrolling. 
Consequently, instruction scheduling is confined to the scope of a single iteration, preventing the effective overlapping of memory access and computation.

We further study this impact by profiling key operators from the \textbf{Qwen2-1.5B} model on the Ascend NPU.
\autoref{fig:perf_stats} presents the ratio of scalar instructions and I-Cache miss rates.
The data reveals that operators in LLMs exhibit a high proportion of scalar instructions and suffer from high I-Cache miss rates.

\textit{Code Bloat in Manually Specialized Libraries.}
High-performance GPU libraries like FlashInfer~\cite{ye2025flashinfer} rely on C++ template metaprogramming to enable aggressive compiler optimizations.
To avoid runtime JIT overhead, these libraries pre-instantiate kernels for the Cartesian product of all template parameters.
As described in \autoref{eq:flash_attention}, FA's configuration space includes head dimensions ($d_k \in \{64, 128, 256\}$), mask types, GQA sizes, and position encodings.
Combined with tile size configurations, this results in over 1000 binary instantiations, yet a specific model like \textbf{Qwen2-1.5B} utilizes only $\sim$10 kernels.
This pre-instantiation strategy, while manageable on GPUs, is ill-suited for Ascend due to its more complex schedule parameters, forcing Ascend libraries to rely on suboptimal generic kernels.

\subsubsection{Why Is Automatic Kernel Specialization Beneficial?}

\autoref{fig:param_stats} reveals that the overwhelming majority of kernel parameters are runtime invariants.
Propagating \initialconsts to resolve schedule parameters at compile time yields two benefits: (1) for generic kernels, it enables model-specific specialization with aggressive constant folding, reducing scalar overhead and I-Cache misses; (2) for manually specialized libraries, it makes kernel dispatch paths deterministic, enabling precise pruning of unused binaries.

\subsection{Challenges and Design Insights}
\label{sec:motivation:challenges}

Achieving automatic kernel specialization requires analyzing the value flow from Python down to C++, which presents two major challenges that cannot be properly addressed by existing static analysis.

\subsubsection{Challenge 1: The cross-language semantic gap.}

Achieving high-precision, context-sensitive cross-language analysis fundamentally relies on the accurate reconstruction of the calling context for C++ operators. 
Modern DL systems extensively leverage FFI mechanisms (e.g., Pybind11~\cite{pybind11}, CPython C API~\cite{pythoncapi}) to invoke underlying C++ operators, whose input parameters (e.g., Tensors) are typically instantiated and initialized on the Python side. 
However, the FFI layer is replete with complex \textit{glue code}, involving implicit type conversions, dynamic dispatch mechanisms, and reference counting, which creates a significant semantic gap between Python and C++. 
This poses a severe challenge for traditional source-based cross-language analysis methods.

Existing cross-language analysis works~\cite{kan2024taint4javac,Monat2021PythonC} primarily rely on abstract interpretation techniques to address general multi-language interoperability issues (e.g., Python-C, Java-C). 
Nevertheless, these methods face significant challenges when applied to DL systems due to two main limitations:
(1) \textbf{Lack of Domain Awareness:} Existing tools typically model generic FFI APIs as black boxes, failing to comprehend the complex \textit{domain-specific objects} within DL systems, particularly the deep heap memory layouts and internal indirect reference relationships.
(2) \textbf{Efficiency and Precision Bottlenecks:} Performing full interpretation of dynamic language source code is inefficient and struggles to accurately deduce the side effects of complex C++ internal heap allocations from the Python side.

\textit{Insight: Semantic modeling of core data types in DL systems.}
Instead of the traditional paradigm of analyzing FFI control flows, we propose a cross-language semantic modeling approach grounded in two observations:
(1) \textbf{Finite and Stable Core Types:} Data types used for cross-language interaction in DL systems are highly convergent and stable (\texttt{Tensor}, \texttt{Array}, etc.), enabling comprehensive and precise semantic modeling.
(2) \textbf{Extract Constant Information from Graph IR:} DL systems compile models and represent them using Graph IR (e.g. ATen IR), which contains precise information regarding operator input parameters, enabling direct extraction of semantic values without analyzing Python source code.
Building on these insights, we directly map computation graph node information to the abstract states of C++ entry functions, achieving high-precision reconstruction of C++ contexts while avoiding the overhead of analyzing complex FFI glue code.

\subsubsection{Challenge 2: Shape Checkers Leading to Early-Exit Paths}

Operator libraries enforce constraints (memory alignment, dimension equality) through runtime shape checkers.
FA requires matching batch sizes ($B_q = B_k = B_v$) and sequence lengths ($S_k = S_v$); violations trigger early exits with error codes.

\autoref{lst:early_return_code} shows how shape checkers impede optimization.
Function \texttt{set\_t} verifies if sequence lengths match; since dimensions are dynamic, the compiler cannot guarantee the check passes.
Standard path-insensitive analysis merges data flows from success (\texttt{t=32}) and early-exit paths, ``polluting'' the value of \texttt{t} at the exit block (\autoref{fig:set_t_cfg}).
While symbolic execution~\cite{Cadar2008KLEEUnassistedAutomatic,Yao2024FalconFusedApproach} can distinguish paths, it is prohibitively expensive due to path explosion.

\textit{Insight: Conditional Return-Value Flow.}
If we can infer from guard conditions whether return values belong to SUCCESS or ERROR status codes, we can identify early-exit vs. normal paths.
We construct a \textit{conditional value flow graph} for return values, explicitly representing conditional expressions and their corresponding return values, enabling early-exit path identification.
