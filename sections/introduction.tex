\section{Introduction}\label{sec:intro}

DL frameworks and serving systems~\cite{ansel2024dynamo,abadi2016tensorflow,kwon2023vllm,zheng2024sglang} rely heavily on hand-written operator libraries~\cite{nvidia2021cublas,nvidia2017cutlass,ye2025flashinfer,ascend_cannopsadv,dao2024flashattention2,flashmla2025} to ensure efficient operator implementation.
To achieve universal applicability, these libraries must handle \dynamics arising from two main sources: (1) Cross-model heterogeneity, involving diverse algorithmic variants (e.g., attention mechanisms~\cite{vaswani2017attention,ainslie2023gqa,shazeer2019fast,beltagy2020longformerlongdocumenttransformer}) and varying attributes (e.g., head numbers~\cite{yang2024qwen2technicalreport,touvron2023llama2openfoundation,deepseekai2025deepseekv3technicalreport}); and (2) Input shape variability, where dimensions like batch sizes and sequence lengths vary at runtime.
To accommodate such dynamics, operator libraries typically adopt a generic implementation strategy: they calculate \textit{schedule parameters} (configuration values such as tiling sizes and loop bounds) at runtime typically on the Host and pass them to the kernel function as variable arguments.
However, this generic design comes at a cost.
From the perspective of the underlying device native compiler, these critical configuration values appear as unknown variables rather than compile-time constants.
This ambiguity effectively disables aggressive compiler optimizations that rely on static information, such as constant folding, loop unrolling, and precise register allocation, often leading to suboptimal register usage and thereby limiting the performance potential of the generated binary.
In this background, specializing kernels by replacing input schedule parameters with constants at compile time is generally beneficial, as it can enhance subsequent compiler optimizations.
As the complexity of operators~\cite{dao2024flashattention2,ye2025flashinfer} continues to increase and programmable units~\cite{liao2019davinci,jouppi2023tpu} within hardware become increasingly diverse, consequently the number of schedule parameters of kernels explodes, which further necessitates the kernel specialization.

Existing operator libraries adopt different specialization strategies depending on the underlying hardware characteristics, yet both approaches face critical limitations as illustrated in \autoref{fig:comparison-libraries}.
On GPU platforms, which are highly sensitive to compiler optimizations like loop unrolling, developers usually resort to manual specialization using C++ templates~\cite{nvidia2017cutlass,ye2025flashinfer,dao2024flashattention2} (depicted as \ding{183}).
While this resolves control-flow-related parameters at compile-time, exhaustively enumerating parameter combinations to accommodate input dynamics leads to combinatorial explosion and severe code bloat.
Conversely, on architectures like Ascend~\cite{liao2019davinci} that provide diverse programmable units, the schedule parameters are significantly more numerous.
Since manually specializing for such a vast search space is intractable, the vendor libraries (e.g., CANN~\cite{ascend_cannopsadv}) on such platforms primarily invoke generic kernels (depicted as \ding{182}), resulting in performance loss due to missed compiler optimizations.
While AI compilers~\cite{tillet2019triton,chen2018tvm,zheng2022dietcode,shen2021nimble,zheng2023bladedisc} offer an alternative by generating specialized kernels at runtime, they are typically confined to specific high-level IRs (e.g., Triton IR and Relax~\cite{Lai2023RelaxCA}) and incur non-negligible runtime compilation overhead.
Focusing on hand-written operator libraries, the goal of this paper is twofold: \textit{achieving automatic specialization for generic libraries to recover the Performance Loss, and performing pruning for manually specialized libraries to mitigate the combinatorial explosion and code bloat}.

Moreover, deploying a specific model exhibits \partialdynamics.
While inputs involve dynamic dimensions like batch size, model-specific attributes (e.g., hidden size, head number) and algorithmic variants are determined at compile time and remain invariant throughout the serving phase.
We denote these immutable values as \initialconsts, which can be resolved by symbolic shape inference in current DL frameworks~\cite{shen2021nimble, zheng2023bladedisc, Lai2023RelaxCA, ansel2024dynamo}.
\textbf{A key insight is that schedule configurations of kernels are mainly determined by these \initialconsts.}
Our analysis (detailed in \S\ref{sec:motivation}) reveals that given \initialconsts, over 90\% of the kernel schedule parameters become deterministic.
This suggests that the vast majority of dynamic schedule decisions inside kernels can effectively be resolved statically before execution.

Based on this insight, we propose leveraging the \initialconsts as the contextual information to perform whole-program constant propagation.
By propagating these \initialconsts through the operator library down to the kernel call sites, we can statically specialize generic kernels and prune redundant instances in manually specialized libraries.
However, implementing this strategy faces two critical challenges regarding the precision of static analysis: the \textbf{cross-language boundary} and \textbf{complex control flows}.
First, the operator library is typically integrated into the framework via Python/C++ Foreign Function Interface (FFI), which cuts off the traditional static call graph.
Second, the Host-side programs of operators involve many shape checkers for input validity, introducing numerous early-exit paths that return error status codes when shape constraints are violated.
Standard static analysis conservatively merges data flows from these early-exit paths with the normal path, polluting the precise constant information and causing significant precision loss (i.e., treating constants as "unknown" at merge points).

To address the above challenges, we introduce \mysys, the first system designed to analyze cross-language constant propagation for kernel specialization. 
We construct an automated cross-language and whole program analysis framework for automatic specialization of generic library kernels and code debloating for manually specialized libraries.
By introducing mechanisms specific to DL systems, \mysys extends traditional static analysis techniques and consists of three main components:

\begin{itemize}
    \item \textbf{Cross-Language Context Reconstruction:} 
    Instead of analyzing the complex FFI implementation or Python source code, \mysys employs domain-aware semantic modeling for core DL data types. 
    This approach allows us to directly map high-level operator attributes and tensor metadata to the memory offsets of C++ operator arguments, thereby reconstructing the precise calling context.

    \item \textbf{Information Propagation:} 
    This module performs context-sensitive inter-procedural analysis to propagate constants through complex Host-side programs. 
    It integrates a conditional return-value flow analysis to identify early-exit edges---control-flow edges that lead to error returns when shape checkers fail. 
    By constructing a lightweight value flow graph for return values and determining error states through simple constant comparison against predefined status code sets, \mysys precisely identifies and prunes these early-exit edges, enabling accurate constant propagation along valid execution paths.

    \item \textbf{Kernel Specialization:} 
    Utilizing the propagated invariants, this module performs IR-level transformations. 
    For generic libraries, it specializes kernels by substituting variable arguments with constants and then applies aggressive compiler optimizations. 
    For manually specialized libraries, it identifies and eliminates redundant template instantiations, achieving significant library debloating.
\end{itemize}

In summary, the main contributions of this paper are as follows:
\begin{enumerate}
    \item We propose \mysys, a novel static analysis framework that, for the first time, achieves precise constant propagation across the DL framework's language boundary (Python/C++) into the underlying operator libraries.
    \item We introduce a cross-language context reconstruction method and a conditional return-value flow analysis for identifying early-exit edges, effectively overcoming the barriers of FFI gaps and complex shape checkers that hinder standard static analysis.
    \item We implement \mysys based on LLVM~\cite{lattner2004llvm} and apply it to PyTorch~\cite{ansel2024dynamo}. The system is designed with extensibility, applicable to other Python-based frameworks (e.g., TensorFlow) and various hardware backends supported by LLVM.
    \item Evaluation on different platforms demonstrates the effectiveness of \mysys.
    For generic operators of Ascend, it achieves an average speedup of 1.06$\times$ (up to 1.17$\times$) and 1.03$\times$ end-to-end inference speedup on top of highly optimized vendor libraries.
    For manually specialized libraries, \mysys removes over 96\% of redundant kernels, solving the code bloat issue while maintaining optimal performance.
\end{enumerate}
